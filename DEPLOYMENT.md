# Deployment

How OASI runs on AWS, how changes get there, and how to operate it.
Written in English like the rest of the infrastructure; the app's user-facing
text stays in Spanish.

**Quick reference** (details below):

| I want to… | Do this |
|---|---|
| Ship a change to dev | merge/push to `develop` in both repos |
| Ship dev to prod | open a PR `develop → main`, merge it |
| Try a change before it deploys | [run locally](#1-local-development) |
| Try my local frontend against the real dev API | `npm run dev:aws` in `proyectos-frontend` |
| Check the database of an environment | `scripts/db-ops.sh dev status` |
| Add a database change | new file in `db/migrations/` + same change in `db/schema.sql` ([rules](#adding-a-database-change)) |
| See why the API failed | CloudWatch → Log groups → `/aws/lambda/oasi-<stage>-api` |

---

## Environments

Two complete, independent copies of the system. Nothing is shared between
them — not the database, not the users, not the files.

| | **dev** | **prod** |
|---|---|---|
| Git branch (both repos) | `develop` | `main` |
| Website | Amplify branch `develop` | Amplify branch `main` |
| API | `oasi-dev-api` Lambda | `oasi-prod-api` Lambda |
| Database | RDS `t4g.micro`, 1-day backups | RDS `t4g.micro`, **14-day backups, deletion protection** |
| Users | Cognito pool `oasi-dev` | Cognito pool `oasi-prod` (separate accounts) |
| Internet egress for the Lambdas | NAT **instance** (~US$3/mo) | NAT **gateway** (~US$32/mo, highly available) |
| Deleting the stack | wipes everything | refuses (termination protection); DB, pool, bucket are retained |
| Deploy approval | automatic on push | automatic on merge, optionally gated by a reviewer ([GitHub setup](#3-github-one-time)) |

Per-environment settings live in **one file**: [`infra/lib/config.ts`](infra/lib/config.ts).

### What each environment contains

```
Browser ──► Amplify Hosting (React build)
   │
   ├──► Cognito (sign-in, JWT)
   │
   └──► API Gateway ──► Lambda "api" (Express) ──► RDS PostgreSQL
                              │                    (isolated subnet,
                              ├──► S3 (attachments) no internet route)
                              └──► Secrets Manager (DB password)

GitHub Actions ──(OIDC)──► CDK deploy ──► Lambda "db-ops" ──► migrations
```

| Piece | Service | Why this way |
|---|---|---|
| Network | VPC, 2 AZs, public / private / isolated subnets | The DB has no route to the internet at all; Lambdas only reach out through NAT |
| Database | RDS PostgreSQL 16, `t4g.micro`, gp3, encrypted | Graviton is cheaper than `t3` for the same size |
| DB password | Secrets Manager, generated by CDK | Never in code, env vars or git |
| API | Lambda (Node 24, ARM) + API Gateway REST | The same Express app as local, via `serverless-http` |
| db-ops | Lambda in the VPC, no HTTP endpoint | Migrations and one-off DB tasks without a tunnel, bastion or public DB |
| Attachments | S3, private, presigned URLs | The browser uploads directly; the API never proxies files |
| S3 access | Gateway VPC endpoint | Free, and S3 traffic skips the NAT |
| Alarms | CloudWatch → SNS → email | API errors, API 5xx, low DB storage |
| Frontend | Amplify Hosting | Builds from GitHub per branch; not in CDK (needs a GitHub connection) |

### Account-wide (`Oasi-Account`, deployed once)

| | |
|---|---|
| GitHub OIDC provider | GitHub Actions gets short-lived AWS credentials per run. No access keys stored in GitHub |
| `oasi-github-deploy-dev` / `-prod` roles | Each assumable **only** by a job in the matching GitHub Environment of `OASI-CL/proyectos-backend`. They can only assume the CDK bootstrap roles and invoke their own db-ops Lambda |
| Budget `oasi-monthly` | Emails when actual spend passes 80% of US$100, or the forecast passes 100% |

## 1. Local development

The goal is that almost everything is caught before any deploy.

### Backend

```bash
cd proyectos-backend
npm run dev          # API on http://localhost:3001, reloads on save
npm run migrate      # apply pending db/migrations to the local DB in .env
```

`.env` (not committed) for local work:

```
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=oasi_dev
DB_USER=postgres
DB_PASSWORD=oasi_dev_local
AUTH_MODE=dev          # role switcher in the UI; or `cognito` + the COGNITO_* vars
AWS_PROFILE=oasi       # only needed to create users from the app locally
```

### Before pushing: `npm run check`

```bash
npm run check
```

Runs exactly what CI runs, in order:

1. type-check the API
2. type-check the infrastructure
3. build the real Lambda bundle (`dist-lambda/`: compiled JS + production dependencies only)
4. smoke-test that bundle from a copy outside the repo — catches the bugs that
   only exist in Lambda: a dependency in `devDependencies`, a bad `require`
   path, SQL files missing from the bundle, CORS left open

If `npm run check` passes locally, the CI `check` job passes.

To see what a deploy would change in AWS without deploying:

```bash
cd infra && AWS_PROFILE=oasi npx cdk diff Oasi-dev -c stage=dev
```

### Frontend

```bash
cd proyectos-frontend
npm run dev          # against your local API (.env)
npm run dev:aws      # against the deployed dev API and dev Cognito (.env.aws)
```

`.env.aws` (not committed — `.env.*` is gitignored) holds the dev values:

```
VITE_API_URL=<Oasi-dev ApiUrl, no trailing slash>
VITE_COGNITO_USER_POOL_ID=<Oasi-Auth-dev UserPoolId>
VITE_COGNITO_CLIENT_ID=<Oasi-Auth-dev UserPoolClientId>
VITE_COGNITO_REGION=us-east-1
```

This works because the dev API allows `http://localhost:5173` (in
`infra/lib/config.ts`). Prod does not.

## 2. First-time setup

Done once. Kept here so it can be repeated in a new account.

### 2.1 AWS credentials and CDK bootstrap

```bash
aws configure --profile oasi          # IAM user with admin rights, region us-east-1
export AWS_PROFILE=oasi
cd proyectos-backend/infra && npm ci
npx cdk bootstrap                     # once per account + region
```

### 2.2 Account stack

```bash
npx cdk deploy Oasi-Account
```

Outputs the two deploy role ARNs used in [GitHub setup](#3-github-one-time).

### 2.3 First deploy of an environment

CI can do this, but the very first one is simpler from a laptop:

```bash
cd proyectos-backend
npm run build:lambda && npm run test:lambda
cd infra
npx cdk deploy Oasi-Auth-dev Oasi-dev -c stage=dev
```

~15–20 minutes, mostly RDS. Then, from `proyectos-backend/`:

```bash
scripts/db-ops.sh dev migrate                                   # creates the schema + catalogs
scripts/load-data.sh dev                                        # historical data from your local DB (once)
scripts/create-admin.sh dev persona@economia.cl "Nombre Apellido" # first admin (emails a temporary password)
scripts/db-ops.sh dev status                                    # check
```

`load-data.sh` only runs against an environment with no projects yet, so it
cannot duplicate data. The dump travels through the environment's private
bucket and is deleted right after loading.

After deploying, AWS emails a **subscription confirmation** for alarms to the
address in `config.ts` — click it, or alarms are never delivered.

Same steps with `prod` for production.

### 2.4 Amplify (frontend)

1. Amplify console → **Create new app** → **GitHub** → authorize →
   repository `OASI-CL/proyectos-frontend`, branch `develop`.
2. Build settings: Amplify detects `amplify.yml`. Leave it.
3. Create the app. (The first build fails on purpose: `VITE_API_URL` is not
   set yet, and `amplify.yml` refuses to publish a site that would call
   localhost.)
4. Set the variables and the SPA rewrite — from `proyectos-backend/`:

   ```bash
   scripts/amplify-env.sh <amplify-app-id> develop dev
   ```

   It reads the stack outputs and sets, **for that branch only**,
   `VITE_API_URL`, `VITE_COGNITO_USER_POOL_ID`, `VITE_COGNITO_CLIENT_ID`,
   `VITE_COGNITO_REGION`, plus the rewrite `/<*> → /index.html (200)` so deep
   links work, then starts a build.
5. Put the branch URL (`https://develop.<app-id>.amplifyapp.com`) in
   `frontendOrigins` for `dev` in `infra/lib/config.ts`, commit, push to
   `develop`. Until then the API rejects the site's requests (CORS).

For prod: Amplify app → **Add branch** → `main`, then
`scripts/amplify-env.sh <app-id> main prod`, and add
`https://main.<app-id>.amplifyapp.com` to `prod.frontendOrigins`.

## 3. GitHub (one time)

### Backend repo — `OASI-CL/proyectos-backend`

**Settings → Environments → New environment**, twice:

| Environment | Secret `AWS_DEPLOY_ROLE_ARN` | Protection |
|---|---|---|
| `dev` | output `DeployRoleArndev` of `Oasi-Account` | none |
| `prod` | output `DeployRoleArnprod` of `Oasi-Account` | **Required reviewers**: yourself (the merge still deploys, but waits for one click) · **Deployment branches**: selected → `main` |

The role ARNs are not secret in the strict sense (they grant nothing on their
own), but storing them as environment secrets keeps each one scoped to its
environment.

**Settings → Branches → Add branch ruleset** for `main` (and optionally `develop`):

- Require a pull request before merging
- Require status checks to pass → `Type-check, build, smoke-test`
- Block force pushes

This is what makes "prod only receives what went through `develop` and passed
CI" true instead of a convention.

### Frontend repo — `OASI-CL/proyectos-frontend`

Same branch ruleset, with the required check `Type-check, lint and build`.
No secrets: Amplify has its own GitHub connection.

## 4. Day-to-day flow

```
feature work ──PR──► develop ──(CI check → deploy dev → migrate → health check)
                        │
                        │   test on the dev site
                        ▼
                 PR develop → main ──merge──► (CI check → [approval] → deploy prod → migrate → health check)
```

- **Backend**: `.github/workflows/deploy.yml`. Pull requests only run checks
  and never receive AWS credentials. A push to `develop` or `main` builds the
  bundle once, smoke-tests it, deploys that same artifact, runs migrations,
  then calls `/health/db` on the deployed API — a green run means the API
  reaches its database, not just that CloudFormation finished.
- **Frontend**: Amplify builds each branch on push. `ci.yml` checks PRs.
- Deploys of the same branch queue; one is never cancelled halfway.

When a change touches **both** repos (a new endpoint and the page that uses
it), merge the backend first: the frontend build does not depend on it, but
the new page would call an endpoint that is not there yet.

### Adding a database change

1. `db/migrations/NNN_description.sql` — next number
2. **No** `BEGIN`/`COMMIT` inside: the runner wraps each file and its record
   in one transaction, so a failure applies nothing and records nothing
3. The same change in `db/schema.sql`, so a fresh database matches
4. No psql meta-commands (lines starting with `\`)
5. `npm run migrate` locally, test, push. CI applies it after deploying.

Applied migrations are recorded in the `schema_migrations` table; each runs
once per database. The runner is `src/db/migrate.ts`.

Write migrations that are safe while the **previous** version of the API is
still serving (add a column before code uses it; stop using a column before
dropping it). The Lambda switches versions within seconds of the migration,
not atomically with it.

## 5. Operating

| Task | Command / place |
|---|---|
| DB state (migrations, row counts) | `scripts/db-ops.sh <stage> status` |
| Apply migrations by hand | `scripts/db-ops.sh <stage> migrate` |
| API logs | CloudWatch → `/aws/lambda/oasi-<stage>-api` |
| db-ops logs | CloudWatch → `/aws/lambda/oasi-<stage>-db-ops` |
| Re-run a deploy | GitHub → Actions → Backend CI/CD → Run workflow → pick the branch |
| Roll back the API | revert the commit on the branch and push (redeploys the previous code). Migrations are not reverted automatically: write a new one |
| Restore the DB | RDS console → the instance → Maintenance & backups → Restore to point in time (creates a new instance) |
| Cost | Billing → Budgets → `oasi-monthly` |

### Cost estimate (us-east-1, on-demand, monthly)

| | dev | prod |
|---|---|---|
| NAT | ~3 (instance) | ~32 (gateway) |
| Public IPv4 address | ~4 | ~4 |
| RDS `t4g.micro` + 20 GB gp3 | ~14 | ~14 + backups |
| Lambda, API Gateway, S3, Secrets Manager, SNS, CloudWatch | ~2 | ~2 |
| Cognito (under 50k users) | 0 | 0 |
| Amplify Hosting | ~1 | ~1 |
| **Total** | **~24** | **~55** |

Free-tier credits on a new account lower this at first. The budget emails
before surprises.

To pause dev entirely: `cd infra && npx cdk destroy Oasi-dev -c stage=dev`
(deletes its database — dev data only; redeploy + `load-data.sh` to bring it back).

## Roles and access

Five roles. The Cognito group is only a hint — the `usuarios` row is
authoritative, because it holds the *scope*, and a role without its scope
cannot be enforced. `middleware/auth.ts` refuses a scoped role whose scope is
missing rather than falling through to "sees everything".

| Role | Sees | Writes |
|---|---|---|
| `admin` | everything | direct; manages users |
| `oasi` | everything | direct; **approves** what others submit |
| `organismo` | permits of its agency + the projects behind them | proposes edits, OASI approves |
| `empresa` | only its own projects and their permits | proposes new projects/permits, OASI approves |
| `region` | every project of its region, across agencies | read-only |

Row filtering is in `middleware/scope.ts`, server-side, on every query. The
frontend hiding buttons is convenience, not security.

## Known gaps

Real ones, not hypotheticals:

1. **No automated tests** beyond type-checking and the bundle smoke test.
   CI proves the build is sound and the deployed API reaches its database; it
   does not prove business logic.
2. **Single-AZ database.** An AZ outage takes the DB down until AWS recovers
   it; backups protect the data, not the uptime. Multi-AZ doubles the RDS cost.
3. **Cognito email** is AWS's shared sender, capped at 50 emails/day and more
   likely to land in spam. Fine for ~20 users; move to SES with an
   `economia.cl` sender before a large onboarding.
4. **No WAF** in front of API Gateway (~US$6+/month). Throttling (50 req/s)
   is on; every data route requires a valid JWT.
5. **The NAT instance in dev is not self-healing.** If it stops, dev loses
   internet egress (Secrets Manager, Cognito) until it is started again or the
   stack is redeployed. Prod uses the managed gateway.
