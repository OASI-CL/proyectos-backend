# Deployment

How OASI is deployed to AWS, and how to do it yourself.

Everything below is written in English on purpose (the codebase is migrating
that way). The app's user-facing text stays in Spanish.

---

## What gets created

Two CDK stacks in `infra/`:

| Stack | Contains | Cost |
|---|---|---|
| `Oasi-Auth-<stage>` | Cognito user pool, 5 role groups, app client | **free** (50k MAU) |
| `Oasi-<stage>` | VPC, RDS, Lambda, API Gateway, S3 | ~US$50/month, mostly NAT |

Split on purpose: Cognito is the only free piece and the only one needed to
build and test the login, so you can deploy it alone and pay nothing until
the API actually has to be online. For just wiring up sign-in, see
[`infra/COGNITO_SETUP.md`](infra/COGNITO_SETUP.md).

```bash
npx cdk deploy Oasi-Auth-dev -c stage=dev   # free
npx cdk deploy Oasi-dev      -c stage=dev   # starts costing
```

| Piece | Service | Notes |
|---|---|---|
| Network | VPC, 2 AZs, **1** NAT gateway | One NAT, not one per AZ — it is the single most expensive line item (~US$32/mo each) and this does not need NAT redundancy |
| Database | RDS PostgreSQL 16, `t3.micro` | In **isolated** subnets: no internet route, reachable only from the API's security group |
| DB password | Secrets Manager | Generated by CDK. Never in an env var, never in git |
| Auth | Cognito User Pool + 5 groups | `admin`, `oasi`, `organismo`, `empresa`, `region` |
| API | Lambda (Node 22) + API Gateway | Express runs as-is via `serverless-http`; API Gateway proxies everything |
| Attachments | S3 bucket | Private; the browser uploads with a presigned URL |
| Frontend | Amplify Hosting | Connected to the `proyectos-frontend` repo — **not** managed by this CDK stack (see below) |

`npx cdk synth` renders the full template locally without touching AWS, if you
want to read it before deploying.

### Why Amplify is not in the CDK stack

Amplify Hosting needs a GitHub token to connect to the repo. Putting that in
CDK means storing a token in Secrets Manager and granting it repo access, for
something you click once. It is set up through the console instead (steps
below) and then never touched again.

## Prerequisites

- An AWS account and the AWS CLI configured (`aws configure` / SSO)
- Node.js 22+
- `psql` (to run the migrations)
- Permission to create VPC, RDS, Lambda, Cognito, S3 and IAM resources

## First deploy

### 1. Bootstrap CDK (once per account+region)

```bash
cd proyectos-backend/infra
npm ci
npx cdk bootstrap aws://<ACCOUNT_ID>/us-east-1
```

### 2. Build the Lambda bundle

```bash
cd proyectos-backend
npm ci
npm run build:lambda
```

This produces `dist-lambda/` — the compiled JS plus its production
dependencies. The compiled code still does `require('express')`, so the
dependencies have to travel with it.

### 3. Deploy

```bash
npm run infra:deploy -- -c stage=dev
```

CORS is left open on this first pass because the Amplify URL does not exist
yet. Step 6 closes it.

Note the outputs — you need them next:

```
ApiUrl             https://xxxx.execute-api.us-east-1.amazonaws.com/dev/
UserPoolId         us-east-1_XXXXXXXXX
UserPoolClientId   xxxxxxxxxxxxxxxxxxxxxxxxxx
DbEndpoint         oasi-dev-....rds.amazonaws.com
DbSecretArn        arn:aws:secretsmanager:...
```

### 4. Create the database schema

RDS sits in a private subnet with no public route, which is the point — so you
cannot reach it from your laptop directly. Tunnel through SSM (no bastion host
to pay for or patch):

```bash
# Get the password CDK generated
aws secretsmanager get-secret-value --secret-id oasi/dev/db \
  --query SecretString --output text

# Port-forward 5432 to the RDS instance through a managed instance
aws ssm start-session \
  --target <INSTANCE_ID> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<DbEndpoint>"],"portNumber":["5432"],"localPortNumber":["5432"]}'
```

Then, in another terminal:

```bash
cd proyectos-backend
DB_HOST=127.0.0.1 DB_NAME=oasi DB_USER=oasi_admin DB_PASSWORD='<from secret>' \
  npm run migrate
```

`npm run migrate` applies `db/schema.sql` on an empty database, or everything
in `db/migrations/` on an existing one. It picks automatically.

To load the historical data from the spreadsheet, see the "Cargar los datos
del Excel" section in `README.md` — same tunnel, `db/seed.py` instead.

### 5. Set up Amplify Hosting

1. Amplify console → **Create new app** → GitHub → `OASI-CL/proyectos-frontend`,
   branch `main`.
2. Amplify detects `amplify.yml` in the repo — no build config to fill in.
3. **Environment variables** (App settings → Environment variables):

   | Variable | Value |
   |---|---|
   | `VITE_API_URL` | the `ApiUrl` output, **without** the trailing slash |
   | `VITE_COGNITO_USER_POOL_ID` | the `UserPoolId` output |
   | `VITE_COGNITO_CLIENT_ID` | the `UserPoolClientId` output |
   | `VITE_COGNITO_REGION` | `us-east-1` |

   These are inlined by Vite at build time, so changing one needs a redeploy.
4. Add the SPA rewrite so deep links work (App settings → Rewrites and
   redirects): source `/<*>`, target `/index.html`, type **404-200**. Without
   it, reloading on `/permisos/42` returns a 404.

### 6. Close CORS

Now that the Amplify URL exists, redeploy so the API only accepts it:

```bash
npm run infra:deploy -- -c stage=dev -c frontendOrigin=https://main.xxxx.amplifyapp.com
```

### 7. Create the first admin

Cognito holds the account; the `usuarios` table holds the role and the scope.
You need both.

```bash
# 1. Create the user in Cognito
aws cognito-idp admin-create-user \
  --user-pool-id <UserPoolId> \
  --username persona@oasi.gob.cl \
  --user-attributes Name=email,Value=persona@oasi.gob.cl Name=email_verified,Value=true \
                    Name=name,Value="Nombre Apellido"

# 2. Put them in the admin group
aws cognito-idp admin-add-user-to-group \
  --user-pool-id <UserPoolId> \
  --username persona@oasi.gob.cl \
  --group-name admin

# 3. Get their sub
aws cognito-idp admin-get-user \
  --user-pool-id <UserPoolId> --username persona@oasi.gob.cl \
  --query 'UserAttributes[?Name==`sub`].Value' --output text
```

Then insert the row (through the same SSM tunnel):

```sql
INSERT INTO usuarios (cognito_sub, nombre, email, rol)
VALUES ('<sub>', 'Nombre Apellido', 'persona@oasi.gob.cl', 'admin');
```

From here on, that admin creates the rest from **Administración → Usuarios**
in the app. Cognito still needs the account created first (step 1 and 2) —
the app screen assigns the role and the scope.

## CI/CD

### Backend — GitHub Actions

`.github/workflows/deploy.yml`:

- **every push and PR** → type-check the API and the CDK stack
- **push to `main`** → build the Lambda bundle and `cdk deploy`
- pull requests never deploy (they would run PR code with deploy credentials)

Authentication uses **OIDC**, not stored access keys: GitHub asks AWS for a
short-lived token scoped to this repo. To set it up once:

1. IAM → Identity providers → add an OpenID Connect provider for
   `token.actions.githubusercontent.com`, audience `sts.amazonaws.com`.
2. Create a role trusting that provider, restricted to this repo:

   ```json
   {
     "Effect": "Allow",
     "Principal": { "Federated": "arn:aws:iam::<ACCOUNT>:oidc-provider/token.actions.githubusercontent.com" },
     "Action": "sts:AssumeRoleWithWebIdentity",
     "Condition": {
       "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
       "StringLike": { "token.actions.githubusercontent.com:sub": "repo:OASI-CL/proyectos-backend:*" }
     }
   }
   ```

3. Attach the permissions CDK needs (or `arn:aws:iam::aws:policy/AdministratorAccess`
   to start, narrowed later).
4. In the repo: **Settings → Secrets → Actions** → `AWS_DEPLOY_ROLE_ARN`, and
   **Variables** → `FRONTEND_ORIGIN`.

### Frontend — Amplify

Amplify builds from GitHub on every push to `main`; that *is* the frontend
CI/CD, so there is no deploy workflow. `.github/workflows/ci.yml` only
type-checks and lints pull requests, which Amplify does not do.

## Environments

`stage` is a CDK context value, so the same code deploys both:

```bash
npm run infra:deploy -- -c stage=dev
npm run infra:deploy -- -c stage=prod -c frontendOrigin=https://...
```

`prod` differs on the settings that matter when data is real:

| | dev | prod |
|---|---|---|
| Backup retention | 1 day | 14 days |
| Deletion protection (RDS) | off | **on** |
| Removal policy (RDS, Cognito, S3) | destroy | **retain** |
| S3 versioning | off | on |

So `cdk destroy` wipes a dev stack cleanly, and refuses to take the database
and the user pool with it in prod.

## Roles and how access is enforced

Five roles. The Cognito group is only a hint — the `usuarios` row is
authoritative, because that is where the *scope* lives, and a role without its
scope cannot be enforced. `middleware/auth.ts` refuses to authenticate a
scoped role whose scope is missing rather than falling through to "sees
everything".

| Role | Sees | Writes |
|---|---|---|
| `admin` | everything | direct; manages users |
| `oasi` | everything | direct; **approves** what others submit |
| `organismo` | permits of its own agency + the projects behind them | proposes edits, OASI approves |
| `empresa` | only its own projects and their permits | proposes new projects/permits, OASI approves |
| `region` | every project of its region, across all agencies | read-only |

Row filtering lives in `middleware/scope.ts` and is applied server-side on
every query. The frontend hides buttons a role cannot use, but that is
convenience only — the API enforces the same matrix regardless.

### The approval flow

`empresa` and `organismo` never write to `proyectos`/`permisos` directly:

- **Editing** → the change is stored in `solicitudes_cambio` as a proposal.
  The live row is untouched until OASI approves, at which point the update and
  the `historial` diff happen in one transaction.
- **Creating** → the row is inserted with `estado_validacion = 'en_revision'`
  and queued. Approving flips it to `validado`; rejecting leaves it as
  `borrador`, out of every report but not deleted, so nobody loses their work.

That way any number on the dashboard is something OASI has accepted. A partial
unique index allows only one open request per record, so two people cannot
queue conflicting edits.

## Cost estimate

Rough monthly figures for `dev`, on-demand, `us-east-1`:

| | ~US$/month |
|---|---|
| NAT gateway | 32 |
| RDS `t3.micro` + 20 GB | 15 |
| Lambda + API Gateway | < 1 at this volume |
| Cognito | free under 50k MAU |
| S3 + Secrets Manager | ~1 |
| Amplify Hosting | ~1 |
| **Total** | **~50** |

The NAT gateway is the biggest item and exists only so the Lambda can reach
Secrets Manager and S3 from a private subnet. If cost matters more than the
current simplicity, VPC endpoints for those two services remove the NAT
entirely and cut it to roughly half.

## Things to know before going live

These are real gaps, not hypotheticals:

1. **`AUTH_MODE`.** The stack sets `cognito`. If it is ever `dev` in a
   deployed environment, anyone can pick their own role with an HTTP header.
2. **No automated tests.** Everything so far has been verified by hand against
   the real data.
3. **Sign-in has not been tested against a real pool.** The flows are
   implemented and verified end to end against Cognito's actual API (including
   the first-login password challenge and the error mapping), but the only
   pool available while building was a fake id, so the happy path stops at
   "Cognito answered". Worth walking through once with a real user.

The dev role switcher is no longer a concern: it renders only when the Cognito
variables are absent, so a deployed build never shows it.
